# Backblaze B2 PDF storage

Create a **private** bucket and a bucket-scoped application key with read/write file capabilities. The API and worker need `B2_REGION` (the region shown in the bucket endpoint), `B2_BUCKET`, `B2_KEY_ID` and `B2_APPLICATION_KEY`. Store secrets in the deployment secret environment, never the frontend or repository. `PDF_STORAGE_PROVIDER=b2` selects B2; production Compose pins this value. Explicit `local` remains available for development only.

The backend uses the AWS Go S3 SDK against `https://s3.<region>.backblazeb2.com`, as described in [Backblaze's S3 endpoint documentation](https://www.backblaze.com/docs/en/cloud-storage-call-the-s3-compatible-api). Objects use `pdf/<sha256>.pdf`. Uploads are verified before storage and read back to verify their checksum before a source is committed. Downloads, previews, OCR and text review obtain a verified temporary file; no permanent local PDF copy is required. Downloads remain behind the existing application authorization routes, with private/no-store caching and HTTP range support via ServeFile. B2 failures fail the operation without falling back to local assets.

Temporary storage is still needed for PDF parsing/rendering. Imports retain the existing 250 MiB PDF limit, while retrieval has a 1 GiB ceiling for legacy originals. Each concurrent operation can consume a full PDF plus rendering space. The production /tmp tmpfs is 1 GiB; size it for workload concurrency. Temporary files are cleaned on completion/error, and container replacement clears crash leftovers. This version downloads a full original for each preview/download request; range requests do not yet reduce B2 transfer. Account for this when sizing traffic and costs.

## Existing installation migration

1. Back up PostgreSQL and the existing assets volume together. Save the current image and configuration. Configure the private B2 bucket and secrets, and build the updated image.
2. Stop API and worker ingestion/read traffic during cutover. Keep the existing assets volume: production Compose mounts it read-only for migration. No code deletes local originals.
3. With the database running, execute `docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm --no-deps api /app/server -mode migrate-pdfs`. The command reads checksum-named local originals, uploads and verifies each object, then records a verified location in a separate migration ledger. A failure exits nonzero. Fix the failure and rerun; completed ledger entries for the configured bucket are skipped. All revisions retain their source IDs, checksums and immutable provenance snapshots. Historical local paths remain acquisition records; reads resolve by checksum in the configured bucket.
4. Start the updated API and worker with identical B2 configuration. Exercise an authorized original download, page preview and ingestion, and confirm disabled/inaccessible sources remain blocked. Do not claim migration success until all originals and historical citations are accessible.
5. Retain the read-only assets volume through the rollback window. Remove its mount only after backup/restore and remote coverage are established. Never delete it as part of this migration command.

A failed/interrupted migration can leave unreferenced objects or additional B2 versions; rerunning is safe for source identity but may create another object version. Do not configure expiration/deletion of referenced originals. Set retention/versioning and offsite recovery policy deliberately; object storage alone is not a coordinated database-and-assets backup. Roll back to the prior image/configuration with retained local originals; PDFs uploaded after B2 cutover must first be recovered to the legacy checksum layout before rolling back to local-only code.

B2 credentials and live bucket behavior have to be verified in the target deployment. Unit checks use an isolated S3-compatible fixture and do not certify live access or bucket privacy.
